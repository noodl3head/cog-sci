# XH-C5 MSQ Web Mock Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Replace the daily XH-C5 Telegram mock with a link-delivered, exclusive-MSQ web mock that follows the real XH-C5 PYQ distribution of correct-option counts and records reasoning for every option decision.

**Architecture:** Keep the existing daily Telegram cron, chapter-cycle weighting, Neon-backed `telegram_mock_sessions` table, and Telegram subscriber authorization. Change the cron delivery from an inline Telegram quiz to a single deep link containing an opaque, per-session web token. A new authenticated-by-token Next.js page loads a sanitized session, lets the learner mark each option true/false with a checkbox plus a rationale, autosaves responses/reasoning, then submits to the server for all-or-nothing MSQ grading and an in-browser review.

**Tech stack:** Next.js 14 App Router, React 18 client components, Node built-in test runner, Neon/Postgres (`@neondatabase/serverless`), Vercel cron, Telegram Bot API.

- Current data source contains XH-C5 PYQs for 2021–2026. A read-only audit on September 29, 2026 found **103 XH-C5 MSQs**: exactly 6 with one true option (5.8%), 56 with two (54.4%), 40 with three (38.8%), and 1 with all four (1.0%). This supports a weighted, non-fixed cardinality draw for each generated question; do **not** impose a predictable per-mock quota.
- Existing `lib/pyqData.js` is the canonical local PYQ dataset. Existing `getMsqPracticePaper()` combines MSQs from all sections and should remain untouched.
- The user wants an *exclusive MSQ* daily mock, not a full 35-question mock. Retain the current daily size of **10 questions** and the current chapter-cycle / weakness weighting unless later instructed otherwise.
- Reasoning is a personal learning artifact. It must be stored with the web session and exposed in the post-submit review; no new general account/auth system is needed.
- `NEXT_PUBLIC_APP_URL` is the deployment base URL. Fail closed in production if it is absent rather than emitting a broken relative Telegram link.

## Non-negotiable product rules

1. Every question in the new daily mock has `type: 'MSQ'`, four independently judged options, 1 or 2 marks, and all-or-nothing, zero-negative scoring.
2. Correct-option count is selected per question from the empirical PYQ weights `[1: 6, 2: 56, 3: 40, 4: 1]`. Do not display these counts to the learner and do not hard-code a 2/3/1/4 pattern in each daily set.
3. The generator must only select questions whose authored `answers.length` equals the sampled cardinality. It must not add or remove correct answers dynamically, turn MCQs into MSQs, or relabel options to manufacture the distribution.
4. Preserve the existing eligible-topic logic: only topics mapped from attempted chapters can appear, weak topics are weighted higher, and prior session question IDs are excluded.
5. The Telegram message is an invitation and contains one HTTPS link; Telegram is no longer used to answer, submit, or reveal explanations for this daily mock.
6. On the web page, each option is evaluated independently:
   - a checkbox means “I judge this option true/correct”;
   - unchecked means “I judge it false/incorrect”;
   - both states require a written rationale before final submission;
   - after focus/tap, option wording becomes a small eyebrow label above the rationale field, while the checkbox remains the only selection control.
7. Correct answers, explanations, and cardinality are never sent by the read endpoint; only the submit endpoint may grade and reveal them.

export function summarizeXhC5Msqs(papers) {
  const rows = papers.flatMap((paper) => paper.questions
    .filter((question) => question.section === 'XH-C5' && question.type === 'MSQ')
    .map((question) => ({ year: paper.year, question })));

  const correctOptionCounts = { 1: 0, 2: 0, 3: 0, 4: 0 };
  const byYear = {};
  for (const { year, question } of rows) {
    correctOptionCounts[question.answers.length] += 1;
    byYear[year] = (byYear[year] || 0) + 1;
  }
  return { total: rows.length, correctOptionCounts, byYear };
}

**Step 3: Implement the pure selection helper**

Create `lib/xhC5DailyMsqCore.js` with:

```js
export const XH_C5_MSQ_CARDINALITY_WEIGHTS = { 1: 6, 2: 56, 3: 40, 4: 1 };

export function correctOptionCountFor(rng = Math.random) {
  const threshold = rng() * 103;
  let cumulative = 0;
  for (const count of [1, 2, 3, 4]) {
    cumulative += XH_C5_MSQ_CARDINALITY_WEIGHTS[count];
    if (threshold < cumulative) return count;
  }
  return 4;
}
```

Implement `selectDailyXhC5Msqs({ candidates, topicWeights, excludedIds, size, rng })` with these exact rules:

- reject anything not `type === 'MSQ'`, anything outside an eligible topic, anything excluded, and any question without 1–4 authored answers;
- on each draw, sample a cardinality using `correctOptionCountFor(rng)`;
- choose only remaining candidates with that `answers.length`; weight topics using the existing pool-normalized technique from `weightedPick` in `lib/telegramMockCore.js` so huge source pools do not erase weaker topics;
- if the exact cardinality has no eligible candidate, use the nearest available cardinality **only for that question**, preferring absolute distance then the lower count. Return a diagnostic field only in development/tests; never disclose fallback/cardinality to the learner;
- remove each selected question from the pool; throw a clear error if fewer than `size` eligible MSQs exist.

Do not duplicate `weightedPick`; export it from `lib/telegramMockCore.js` or move it into a small shared pure helper, update its existing tests, and import it from both selectors.

## Risks, tradeoffs, and open questions

1. **Auth model:** An opaque 256-bit URL token is sufficient for this single-user workflow and avoids a new login system, but anyone who receives the link can open the test. Do not forward Telegram messages. If this becomes multi-user, replace opaque-link-only access with signed user authentication.
2. **Question-bank workload:** The existing imported AP MCQ bank cannot truthfully become MSQ content by merely splitting answers. The reviewed original MSQ bank is deliberate authoring work; quality is more important than fast volume. Start with at least 120 items, then monitor topic/cardinality depletion.
3. **Requirement interpretation:** This plan preserves the existing 10-question daily size. If “mock” is intended to mean a full 35-question XH-C5-only paper, change `size: 10`, page pacing, and bank-size requirement before implementation.
4. **Rationale burden:** Requiring all four rationales on all 10 questions produces 40 fields. This directly serves the user’s stated metacognitive goal but is time-intensive. The page must show progress and autosave reliably so this does not become frustrating.
5. **Distribution fidelity:** Independent weighted draws are faithful over repeated questions but not guaranteed to reproduce the exact 6/56/40/1 ratio in each 10-question mock. That variability is intentional: it prevents learning a count pattern. The fallback rule must be monitored so sparse topics do not systematically distort rare 1- or 4-correct items.
6. **Legacy Telegram sessions:** Do not delete callback handlers until active old sessions are gone. New link sessions and old callback sessions must not collide on the same date during rollout.
7. **PYQ data quality:** The source audit assumes the locally stored 2021–2026 XH-C5 MSQs are complete and correctly keyed. Before treating the profile as final, compare paper/year counts with the official source files already used by the project and correct any local transcription defect.
